# ADR 0003:安全边界策略与分层加固

- 状态:已接受(首批已落地)
- 日期:2026-07-04
- 背景:一次对全链路(危险分级 / Telegram / Web / 供应商 / 记忆)的自审,结论沉淀于此。
  原始的逐份审计报告是一次性会话产物、依赖具体代码行号、会随代码演进失效,故不入库;
  其结论、威胁模型与落地状态收敛为本 ADR。

## 背景

vococo 是**单用户、自托管**的个人助理:默认 `bypassPermissions`(工具自动执行)、
无沙箱、Agent 拥有完整 Bash/Write,且这个 Agent 挂在网络通道(Telegram/Web)上。

## 决策:一个根因,四层策略

### 根因

五处「严重/高危」发现收敛到**同一个架构事实**:

> 一旦有人能对这个 Agent 说话,就等于拿到了本机的任意代码执行。

之后所有花样——黑名单绕过、改危险分级源码、偷 env 里的 key、cron 后门、记忆投毒——
都是**同一把 RCE 的下游利用**,不是若干个独立的洞。因此真正决定安全的是两件事:
**谁能对 Agent 说话(边界)** 和 **注入发生后能炸多大(爆炸半径)**。

### 四层

```
Tier 0  边界 fail-closed        缺配置=拒绝,而非放行
Tier 1  缩小注入爆炸半径         假设注入一定发生,让它炸得尽量小
Tier 2  纵深防御 / 提高门槛       明确标注「非边界,只是减速带」
Tier 3  根治(长期)             沙箱 / 降级 bypassPermissions
```

- **Tier 0 —— 边界 fail-closed**:Telegram 白名单为空时拒收(要开放须显式 `TELEGRAM_ALLOW_ALL=1`);
  Web 绑非本机却无 `WEB_AUTH_TOKEN` 时拒绝启动;未授权者静默丢弃,不回执 chat_id。
- **Tier 1 —— 缩小爆炸半径**:审批弹窗固定发给主人而非本轮发起人;记忆 / USER.md / 召回历史 /
  反思循环一律套 `<memory_data>` 数据围栏 + 反注入元指令;转发消息标注为不可信数据;
  第三方 key 尽量不落进子进程 env。
- **Tier 2 —— 提高门槛(非边界)**:常量时间比较口令、去掉 query token;cron 工具纳入审批、
  建议展示 prompt 全文;`/browse` 限白名单根;Web stdio MCP 默认禁;`base_url` 校验 scheme +
  精确匹配官方 host;hook 异常 fail-closed;黑名单补灾难级命令(`find -delete`、解释器删根)。
- **Tier 3 —— 根治(长期)**:执行沙箱(容器 / `sandbox-exec` / 受限账号);把
  `bypassPermissions` 从默认值降级,处理不可信内容的会话强制降权。

## 落地状态(2026-07-04)

Tier 0 全部、Tier 1 大部、Tier 2 大部已落地并配套测试。仍挂起:
- **审批发给主人**:群聊会话一律禁自批;单用户私聊本就=主人,跨端路由未做。
- **第三方 key 移出子进程 env**:需 SDK 支持进程内认证,当前无干净路径,未硬改(避免破坏第三方可用性)。
- **自身代码 / 记忆写入 escalate**:开发期自我迭代高频,暂缓;产品稳定后再对源码写入加审批。
- **Tier 3 沙箱**:立项评估中。

新增 fail-closed 开关:`TELEGRAM_ALLOW_ALL`(默认 0)、`WEB_ALLOW_STDIO_MCP`(默认 0)。

## 三条不变的原则

1. **黑名单是减速带,不是墙。** 危险分级里补再多正则也补不完;它拦手滑,不拦恶意。
   任何「加规则」的改动,注释和文档都要写清「这不构成安全边界」。
2. **fail-closed,不 fail-open。** 缺配置、无人应答、hook 异常——一律当「拒绝」处理。
3. **注入一定会发生,设计爆炸半径。** 用户自己转发带毒内容无法 100% 防;重心是让单次注入炸得尽量小。

## 反悔成本

低。各项都由 `.env` 开关独立控制,可逐条回退到纯 bypass 行为。
