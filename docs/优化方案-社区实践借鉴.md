## 优化 1:同会话串行化 + 跨会话并发

**现状问题**:`gateway/run.py` 的 `_serve()` 用 `async for ... await _dispatch` 逐条处理,
导致①一个慢会话(如查资料 2 分钟)会卡住同平台**所有**其他会话;②私聊 UNIFY 共享 `main`、
cron 主动推送等场景下会并发写 `state.db`、编辑同一条 TG 消息,可能状态错乱。

**改法**:给每个 `session_key` 一把 `anyio.Lock`,消息改成**并发派发 + 同会话加锁**:
- `_serve` 里 `self._tg.start_soon(self._dispatch, ...)` → 不同会话并发跑。
- `_dispatch` 内 `async with self._lock_for(inc.session_key)` → 同会话排队串行。
- `_dispatch` 整体 try 兜底(start_soon 子任务抛异常会炸 nursery),原逻辑挪到 `_handle`。

**验证结果**:
- 同会话两条消息 → 时间线 `start,end,start,end`(严格串行)✓
- 跨会话两条消息 → 时间线 `start,start,end,end`(并发重叠)✓
- 每会话独立锁、同键复用 ✓

## 优化 2:主动式 Heartbeat 自检(默认关)

**现状问题**:已有 cron 调度,但 `_write_heartbeat()` 只写 liveness 时间戳,cron 任务都是
**预定义固定**的。缺「让 agent 定时自己看一眼、判断此刻要不要主动提醒你」这层(proactive)。

**改法**:`config.py` 加 `PROACTIVE_*` 配置(默认关);`scheduler.py` 加 `_read_directive` +
`_proactive`,接入 `run_scheduler` 主循环(和 `_reflect` 同款 cron 调度)。逻辑:
- 读 `AI_BRAIN/HEARTBEAT.md`,去掉注释行/空行 → 没实质内容就**跳过,不调 API**。
- 有内容 → 让 agent 判断:没事回 `HEARTBEAT_OK` → **静默不推送**;有事 → 推送到 `PROACTIVE_TARGET`。

**验证结果**:
- 空/纯注释清单 → 返回空串、完全不调 LLM(省额度)✓
- 有内容 → 只留实质行(去掉注释)✓
- agent 回 `HEARTBEAT_OK` → 静默不推送 ✓
- agent 有话 → 推送到目标 ✓

**启用方式**:
```bash
echo "# 每行一件想让 Hermes 主动盯的事" > ~/AI_BRAIN/HEARTBEAT.md   # 空文件=不启用
# 在项目 .env 里:
PROACTIVE_ENABLED=1
PROACTIVE_TARGET=telegram:<你的chat_id>
PROACTIVE_CRON=*/30 * * * *   # 默认每30分钟,可调
```

## 优化 3:记忆加固

**问题 A —— 记忆「存了却没被读」(社区头号失败点)**:
`core/prompt.py` 的 system prompt 原本只拼 PERSONA + USER.md,`AI_BRAIN/MEMORY.md` 索引
**根本没注入**,agent 不知道有哪些记忆,自然想不起来 `recall_past`。
→ 新增 `_load_memory_index()`,把索引(通常几十行,成本极低)注入 system prompt。

**问题 B —— 摘要过长污染索引**:`save_memory` 的 `summary` 会写进 MEMORY.md 索引,
过长既污染索引又增加注入成本。→ 加 `_SUMMARY_MAX=120`,超长打回让 agent 压成一句话(正文放 body)。

**验证结果**:
- MEMORY.md 索引进了 system prompt(内容可见 + 有「长期记忆索引」标题)✓
- MEMORY.md 缺失时不崩 ✓
- 超长 summary(200 字)被拒绝、正常 summary 放行 ✓
